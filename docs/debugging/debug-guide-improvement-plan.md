# 调试引导改进计划

来源记录：`MCP_DEBUG_DELAY_NOTE.md`

## 这次体验为什么会慢

- 第一轮把普通运行日志、编辑器日志和真正的 `ScriptDebugger` 栈混在一起看了。
- 流程没有先确认 `no_active_sessions` 代表的是前置条件未满足，所以在没有活跃会话时就进入了调试路径。
- 前期步骤偏向“先大范围排查”，而不是先确认项目已经运行、调试器数据已经可读。
- 最短路径没有被明确出来：先启动项目，确认活跃会话，再读调试栈，最后才定位到源码行。
- 只看了启动后很短时间内的正常状态，没有把仿真后半段、异步提交和时序相关的错误覆盖进去。
- 曾经用过 `request_debug_break` 之类的人为断点，结果看到的是“人造 break”，不是游戏自然跑到错误点后的真实栈。
- 这次复盘说明，问题不只是 debug 引导，而是 `mcp_start_here` 还没有承担“全功能入口页”的职责。
- 对其他高频工具调用路径，也缺少足够明确的最短路径摘要，导致 agent 仍然需要自己猜下一步该用什么工具。

## 应该怎么改

### 1. 把调试路径的起点改成前置条件确认

- 只要用户是在排查 debug，首步就应该先检查项目是否已经运行。
- 如果没有活跃会话，第一动作应该是启动项目。
- 只有在确认存在活跃会话之后，才进入线程和栈帧读取。

### 2. 把调试栈提升到第一优先级

- 引导里要明确：`ScriptDebugger` 的栈信息是运行时错误的主线证据。
- 控制台日志和大范围扫描只应该作为辅助信号。
- 错误定位应该尽早收敛到具体文件和行号，而不是先扫一圈再说。

### 3. 去掉首轮推荐里的绕路

- `mcp_start_here` 的调试入口要把最快的路线放最前面。
- 只要有工具能直接回答问题，就应当直接点名，而不是先引导到广泛搜索。
- 要明确区分“确认运行态”和“查看日志”，避免两者在首轮被混用。

### 3.1 把 `mcp_start_here` 改成全功能起步页

- `mcp_start_here` 不应该只给 debug 路线，而要给各高频能力的最短工具链。
- 常见入口至少要覆盖：调试、运行态、健康检查、场景、节点、脚本和项目常用操作。
- 对每一类能力，都要让 agent 一眼看到“先用哪几个工具”，而不是只知道“去某个分类里找”。
- 入口页的目标不是罗列全部工具，而是先给最常用的调用路径，减少首次决策成本。

### 4. 把回退规则写死

- 只有在 MCP 里没有相关工具时，才考虑退回 CLI 绕路。
- 如果会话没有启动，先启动项目，再继续问调试细节。
- 如果已经能直接读到调试器栈，就不要先扫无关文件。

### 5. 区分真实错误触发和手动断点

- 不要用 `request_debug_break` 代替真实的错误触发。
- 如果要看真正的报错路径，就让游戏自然跑到错误点，再进入 break 状态。
- 人为断点只适合辅助排查，不适合替代真实的异常栈。

### 6. 覆盖异步和时序型问题

- 只做“启动成功”验证不够，还要让仿真跑到足够后面的状态。
- 对于 `sync can only be called after a submit` 这类问题，必须覆盖提交后同步的时序窗口，而不是只看前 1 到 2 秒的静态正常状态。
- `ui_accept`、`ui_cancel` 这类输入动作只能证明输入通路可用，不能证明计算或提交链路已经走到了目标状态。
- 需要把“运行起来了”与“已经跑到会触发时序错误的阶段”区分开。

## 推荐流程顺序

1. 确认项目正在运行。
2. 确认当前存在活跃运行时会话。
3. 读取调试线程和当前栈。
4. 把错误定位到文件和行号。
5. 只查看相关源码和上下文。
6. 只有在栈信息解释不清楚时，才去看更宽泛的日志。

## 后续文档动作

- 更新 `mcp_start_here` 的引导，但不要只覆盖 debug。
- 为各个高频功能补上最常用的工具流程，让 agent 一读就知道该从哪里下手。
- 给每个高频功能补一个“最短工具链”摘要，让 `mcp_start_here` 不只是目录，而是起步页。
- 把这些摘要写成“先做什么，再做什么”的顺序，而不是静态分类列表。
- 在工具参考和主 README 的引导说明里补一段短的调试检查清单。
- 加一个从 `no_active_sessions` 开始的示例，再加一个从真实栈信息开始的示例。
- 再加一个覆盖异步/时序错误的示例，说明为什么不能只验证启动态。
- 再补一组高频非 debug 场景的示例，例如场景操作、节点创建/修改、脚本读写、项目健康检查和运行态确认。
- 把“必须先有运行态”这条规则写得足够醒目，避免以后再次绕路。
- 给 `mcp_start_here` 附上跨功能的快速入口摘要，例如调试、运行态、健康检查、场景操作、节点操作、脚本操作和项目常用操作。
- 说明 `mcp_start_here` 里哪些内容应该直接指向常用工具链，例如 `run_project`、`get_runtime_info`、`get_debug_threads`、健康检查类工具和场景/节点/脚本的常用操作。
- 说明哪些问题必须等真实错误自然触发，哪些问题可以用人工断点辅助，但不能替代真实栈。

## 成功标准

- 新来的 agent 一眼就能看出：调试工作要先确认运行态和会话状态。
- 引导默认把调试栈检查当作第一步，而不是后置步骤。
- 大范围日志扫描变成 fallback，而不是首选。
- 错误报告能更早收敛到文件和行号。
- 新来的 agent 也能从 `mcp_start_here` 直接看到各个常用功能的最短工具链，而不是只看到 debug 路线。
- 当某个能力在 MCP 里有对应工具时，默认优先 MCP 工具链，只有缺工具时才退回 CLI。
- 调试指引里能明确告诉 agent：什么时候该等真实错误，什么时候可以用人工断点辅助。
- 调试指引还能告诉 agent：什么时候必须让仿真继续跑下去，不能只看启动态。
- 非 debug 的高频工具调用路径也能从入口页直接进入最短链路，而不是先让 agent 自己猜分类。

## 落地顺序

1. 先改调试引导文案。
2. 再补各功能的最短路径摘要。
3. 再补无会话时的回退示例。
4. 再补真实错误触发和手动断点的区分说明。
5. 再补异步和时序错误的示例。
6. 最后从头读一遍，确认首条推荐既覆盖 debug，也覆盖其他高频功能的最常用工具链。
